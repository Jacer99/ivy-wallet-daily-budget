Name:        PocketMoney (one word, camel-cased)

--- Icon concept --------------------------------------------

Base:        Flat-vector wallet, brown leather, with a single
             banknote sticking out the top.
Style:       Filled flat vector, 2-3 colors, thick dark outline.
             No gradients, no shadows, no glossy effects.
Files:       app/src/main/res/mipmap-*/ic_launcher*.webp
             plus ic_launcher_foreground.xml (adaptive icon,
             foreground layer only; background is a solid color).

--- Banknote inspiration: Tunisian dinar (TND) --------------

The green banknote in the icon should evoke the design language
of Tunisian dinar bills, not a generic US dollar bill.

Concretely:
  Color:     Green/teal matching the 5 TND note. Muted,
             desaturated. NOT dollar-bill green. Suggested hex
             #6B9080 — a sage-teal that reads as "money"
             universally while sitting authentically in the TND
             color family.
  Border:    Subtle geometric arabesque border around the
             banknote edge — a nod to the traditional Tunisian
             engraving patterns on real TND notes.
  Center:    Abstract suggestion of a portrait medallion (real
             TND bills have a historical figure). At icon size
             this reads as a soft circle/oval inside the bill.
             Do NOT attempt a real face.
  Corner:    Optional — a small circular medallion shape where
             a denomination number would be on a real bill.
             Only include if legible at 48dp.

Design rule: at 48dp (smallest launcher density), only two
things must read clearly:
  1. It's a wallet.
  2. A banknote is sticking out.
Everything else (border, portrait, number) is bonus at larger
sizes. Do not sacrifice silhouette for detail.

Do NOT copy:
  - Actual TND bill artwork, portraits, or serial numbers
  - Any real currency's exact layout
  - US dollar, Euro, or generic international bill styling
  - Ivy's leaf icon or its green

The banknote is stylized, not literal. Tunisian character comes
from geometry and color, never from text or faces.

CRITICAL: The wallet must NOT look related to Ivy Wallet's leaf
icon. If a bystander sees both icons side by side, they must not
think they belong to the same app.

Spendaily use green as their brand color. PocketMoney uses warm
clay/brown so the icon reads as "wallet" and the in-app accent
reads as "warm" rather than "budget tool".

CALCULATION.md §20 and §21 lock in the following (these are
decisions, not suggestions):

  - Uncategorized transactions: INCLUDED in budget by default.
    Exclusion is opt-in via category rules only.
  - Account eligibility: separate toggle in our config, NOT
    Ivy's AccountEntity.includeInBalance field.
  - Reservations paid late: converted expense uses the ACTUAL
    payment date. No backdating.
  - Salary payday clipping: local per-month. Payday 31 in
    February clips to Feb 28/29 for that cycle only.
  - Do NOT extend BudgetEntity (per-category budget, different
    concept).
  - Do NOT extend PlannedPaymentRuleEntity (recurring template,
    different concept).
  - Reactive updates for new code: hook
    DataObserver.writeEvents: Flow<DataWriteEvent>, not
    LaunchedEffect(reload()).
  - New entities use Long minor units for money. Never Double.

CALCULATION.md §20 also defines the pool calculation for the
daily ledger. §21 clarifies: the daily engine works exclusively
in allocation entries, not raw transaction amounts.
periodRemaining (shown on the summary card) uses raw amounts;
the daily engine uses allocations. They total to the same figure
at period end because all allocations are clipped to the period.

4. UI / UX DIRECTION (studied 2026-09-15)
================================================================

Reference studied: Spendaily (spendaily.com).
Studied for PRINCIPLES only. Do NOT copy visuals, branding,
colors, icons, or exact layouts.

--- Spendaily core principles extracted ---------------------

1. ONE NUMBER, ONE SCREEN.
   The safe-to-spend number is the hero. Everything else is
   subordinate. No competing numbers above the fold. No charts
   above the fold. No total balance above it.

2. CALM > CLEVER.
   No gradients, no mascots, no gamification, no decoration.
   Ivy's own visual language is already calm. Don't fight it.

3. DECISIONS, NOT DATA.
   Every UI element answers "what can I do now?" — not
   "here is everything."

4. ROLLOVER AS A DAILY DECISION (future idea, not v1).
   Spendaily lets the user decide where today's underspend
   goes: "boost tomorrow," "contribute to a goal," or "split."
   For v1 we keep rollover SILENT (CALCULATION.md §30).
   Possible Task 22 polish: optional "where does today's
   leftover go?" bottom sheet.

5. NO-SPEND / STREAKS.
   Spendaily has streaks. We do NOT (SPECIFICATION.md §91
   forbids gamification in v1). But tone matters: if we ever
   add "you spent nothing today," it must be a calm statement,
   never a reward animation.

6. CALENDAR HEATMAP (future idea).
   Spendaily shows a month view with day-by-day status (under /
   on-track / over / no-spend / payday). Strong candidate for
   Task 21 or Task 22. When we get there: single month grid,
   each day colored by status from the palette, payday marked
   with a small dot. No numbers on days. Just colors + shape.

7. PAYDAY BUDGETING.
   Already supported (BudgetPeriodType.Salary from Task 1).
   UI must show "Left until payday" — never a date.
   Same for other periods: "Left this week", "Left this month",
   "Left in this period."

--- Dashboard hierarchy (committed) -------------------------

From SPECIFICATION.md §6, in strict priority order:

  1. Safe to spend today (large number, primary accent)
  2. Add Expense
  3. Add Income
  4. Period progress (budget, spent, reserved, available, days)
  5. Tomorrow projection
  6. Recent transactions
  7. Existing Ivy content

Items 1–3 must fit above the fold on a normal phone. No
scrolling to see the number. No navigating to a dedicated
budget page.

--- Special states -----------------------------------------

Over-today-but-period-has-money (SPECIFICATION.md §39):
  Hero number: 0.00
  Caption: "You are 12.00 over today's target. Future
            allowances will adjust."
  NO red screen. NO warning icon. NO amber alert.

Budget exhausted (SPECIFICATION.md §40):
  Hero number: 0.00
  Caption: "You have used your available spending budget."
  Calm, factual, no punctuation drama.

No budget configured (SPECIFICATION.md §40):
  Hero area: replaced with
    "Set a spending budget to see what's safe to spend today."
    Plus a setup action button.
  NOT 0.00 — a fake zero would incorrectly imply the budget has
  been exhausted.

Loading (SPECIFICATION.md §60):
  Do NOT show fake zeros while loading. Show a placeholder
  (skeleton, shimmer, or blank) — but never 0.00.

Calculation error (SPECIFICATION.md §57):
  Show a recoverable error state. Never display a number if
  the calculation is known to be invalid. A zero caused by
  "calculation failed" must be distinguishable from "budget
  exhausted."

Last day of period (SPECIFICATION.md §40):
  No tomorrow projection row. Today receives the remaining
  discretionary amount.

  BudgetPeriodResolver.kt
    sealed interface BudgetPeriodType {
        data object Weekly
        data object Monthly
        data class Salary(val payday: Int)
        data class Custom(val start: LocalDate, val end: LocalDate)
    }

    CRITICAL: This is a SEALED INTERFACE, not an enum class.
    Room cannot auto-convert a sealed interface to a column.
    See DynamicBudgetConfigEntityMapper below for how we
    persist it.

    BudgetPeriod(start, end, type) with daysRemaining(today)

    resolve(type, today): BudgetPeriod
      Weekly  -> Monday of current week to next Sunday
      Monthly -> 1st of month to last day of month
      Salary  -> payday of this month to day before payday of
                 next month, clipped for months without that day
      Custom  -> given start to given end

  ExpenseAllocationScheduler.kt
    AllocationMode { TODAY, WEEK, MONTH }
    AllocationEntry(date: LocalDate, amount: Long)
    schedule(amount, date, mode, periodEnd): List<AllocationEntry>

    Guarantees:
      Σ allocations == amount (exact, in minor units)
      All entries > 0
      Dates unique
      Never allocates outside period

  package com.ivy.data.db.migration
  (NOT com.ivy.domain.db.migration — that older package has a
  @file:Suppress("InvalidPackageDeclaration") workaround in a

Migration file style:

8. KEY CONVENTIONS (locked in)
================================================================

Money:
  - Engine uses Long minor units.
  - New entities use Long minor units.
  - TND has 3 decimals. 100.50 TND = 100_500L.
  - Ivy legacy entities still use Double (Account, Budget,
    Transaction, PlannedPaymentRule). We do NOT change those.
    Conversion happens only at the mapper boundary via
    CurrencyMinorUnits.
  - Never Float. Never Double. Never rounding money outside
    the allocation algorithm. Never create or destroy value
    through rounding.

Time:
  - Instant → LocalDate via a ZoneId parameter. The zone is
    NEVER a global constant. It's passed through every layer.
  - LocalDate arithmetic uses epoch days where serialization
    is needed (customStartEpochDay, customEndEpochDay,
    dueEpochDay).

Allocation invariants (tested):
  - Σ allocation amounts == source amount (exact)
  - Zero-amount days omitted from result
  - Schedules never create transactions
  - Never double-count: actual accounting vs guidance are
    separate ledgers

Entity style (matches Ivy's TagEntity):
  - @Keep @Serializable @Entity(tableName="snake_plural")
  - UUID primary key: @PrimaryKey + @SerialName("id")
    @Serializable(with = KSerializerUUID::class)
  - Every column decorated with @SerialName("camelCase")
  - Instant fields: @Serializable(with = KSerializerInstant::class)
  - isSynced / isDeleted: Boolean = false with @Deprecated
    annotation "Obsolete field used for cloud sync. Can't be
    deleted because of backwards compatibility"

DAO style:
  - Read in dao/read/XxxDao.kt: @Dao interface, @Query only.
  - Write in dao/write/WriteXxxDao.kt: @Dao interface.
  - Write uses @Upsert (not @Insert(onConflict = ...))
  - Multi-row tables: saveMany without deleteAll on import
  - Singleton tables: deleteAll then saveMany on import
  - Methods:
      save(value) / saveMany(values)
      deleteById(id) / deleteAll()

Test style:
  - JUnit4 (@Test from org.junit.Test)
  - Kotest assertions (io.kotest.matchers.shouldBe etc.)
  - Backtick test names: `fun \`weekly round-trips\`()`
  - Real objects (no mocks) unless mocking a repository or DAO
  - coEvery / coVerify for suspend DAO functions (NOT every /
    verify — those are for non-suspend)

Backup / export compatibility:
  - IvyWalletCompleteData has every field with = emptyList()
    or = HashMap() default.
  - The pre-existing 450-150.json fixture does NOT contain
    "dynamicBudgetConfig" or "reservations" keys.
  - kotlinx.serialization Json is configured with
    ignoreUnknownKeys = true and isLenient = true.
  - The `backup compatibility with 450 (150)` test guards
    backward compat. Do not break it.
  - encodeDefaults is false by default, so an empty list does
    not appear in exported JSON. The round-trip stability
    assertion (`freshBackupUseCase.generateJsonBackup() shouldBe
    exportedJson`) depends on this.

ID remapping on backup import:
  - Ivy's BackupDataUseCase.accommodateExistingAccountsAndCategories
    does a blunt string-replace of UUIDs across the entire
    backup JSON.
  - This means UUIDs inside our CSV columns
    (includedAccountIdsSerialized /
    includedCategoryIdsSerialized) AND our reservation
    references (categoryId, accountId) get remapped
    automatically for free.
  - Do not break this — no format changes that would break
    substring matching of UUIDs.
  - linkedTransactionId is NOT remapped this way (transaction
    IDs are not deduplicated by Ivy on import). This is a
    known limitation. If a user exports and reimports, the
    reservation's linkedTransactionId may point to a
    transaction that no longer exists. Task 22 could add
    repair logic; not v1.

9. GEMINI-SPECIFIC QUIRKS (learned the hard way)
================================================================

Gemini 3 Flash Preview (the model we use for code generation)
cannot execute Gradle in this environment. It tries ./gradlew,
then .\gradlew, then cmd /c gradlew.bat — all fail on Windows
PowerShell. When it then claims "All tests passed local
verification" or "The implementation is complete and tested",
THAT IS A HALLUCINATION. You run the tests. Always.

Specific failure modes we have caught:

  - Wrong source set: Gemini writes test files to
    src/main/java/... instead of src/androidTest/java/...
    Result: "Unresolved reference 'kotest'" or
    "Unresolved reference 'junit'" on compileDebugKotlin.
    Fix: move the file to androidTest, keeping the package
    declaration the same.

  - Extra or missing closing brace: Gemini's
    multi_replace_file_content sometimes adds `}` or drops
    `}` at the end of a file. After each edit, open the file
    in Android Studio and check the last 3 lines.

  - Wildcard import rewrite: Gemini replaces ~40 specific
    imports with `import com.ivy.data.db.dao.read.*` etc.
    NEVER accept this. Always use individual imports in
    existing files.

  - `not in` instead of `!in`.

  - `verify` instead of `coVerify` for suspend functions.

  - `HALF_DOWN` instead of `HALF_UP` (rounding direction).

  - Column list in hand-written CREATE TABLE doesn't match
    the entity (order, nullability, or type). This causes
    runMigrationsAndValidate to fail with a specific column
    mismatch. Always cross-check against the generated
    schema JSON.

  - Referring to a domain type (like BudgetPeriodType sealed
    interface) from a Room entity — Room cannot auto-convert
    a sealed interface. Use a discriminator string + nullable
    param columns instead.

If Gemini hits quota mid-task (which has happened), its file
writes are NOT rolled back. "File was written" in the tool
log means the change is on disk. DO NOT re-run the whole
prompt after quota resets — check git status + file listing,
then finish only the remaining files manually in Android
Studio.
